Noelia

A shared foundation for .NET microservices: a CQRS pipeline, security and identity primitives, caching, messaging, health probes, resilience and observability. The engine names no driver — where data lives is the operator's decision, and it is made where anyone can read it.

One application, two architectures, three stages

The demo in this repository runs the same todo application as a set of microservices behind a gateway and as a single monolith, in Development, Staging and Production, all from one docker compose. The application code is identical everywhere. Two things differ, and both are decisions somebody wrote down.

Where the state lives

Development keeps the cache, the rate counters and the revocation list in the process. Staging and Production put all three on Valkey. No application code knows which of the two it got — that is what the port cut is for.

Who may look

The operator dashboard is open in Development, needs an operator secret in Staging and Production, and is not composed at all on the gateway — which holds no key and could not verify an operator if it wanted to.

What the answer is when the answer is no

A refused dashboard request is a 404 that looks like every other 404. It never announces that the page exists, which is more than a login screen can say.

The dashboard, in each stage

Real screenshots from a real run, captured from the stack by eng/capture-dashboards.mjs rather than drawn. The dashboard is read-only and value-free: configuration keys appear, configuration values never do.

Security checks, not promises

Every Noelia service runs executable assertions at startup and reports them to the dashboard and the log. They exist because of a class of defect the 5.0 line was built to end: something is registered, and therefore present, but not effective — and nothing in the system notices.

CheckDevelopmentStaging & ProductionWhat it asks
noelia.composition.providers PassPass Does every active module's declared requirement have a registered provider?
noelia.health.readiness-coverage PassPass Does readiness check anything at all, or does it answer 200 over a dead database?
noelia.revocation.degradation WarningPass Is the revocation list shared, or does each replica keep its own empty one?
noelia.headers.browser-baseline PassPass Do the response headers a browser enforces actually reach the browser?
noelia.dashboard.operator-access PassPass Is dashboard access policed, and can it be written to an audit trail?
noelia.jwt.key-separation PassPass Can every service that verifies a token also mint one?

The Warning is the point, not an oversight. Development runs an in-process revocation list, a second replica would not see it, and the check says so instead of letting the stage look like Production.

Run it yourself

Everything below is in this repository under demo/. It needs Docker and nothing else; the Noelia packages come from nuget.org. 

git clone https://github.com/DavidOeztuerk/noelia
cd noelia/demo
cp .env.example .env        # then fill in a key pair and an operator secret

docker compose --profile dev     up -d --build --wait
docker compose --profile staging up -d --build --wait
docker compose --profile prod    up -d --build --wait
docker compose --profile all     up -d --build --wait
AddressWhat is behind it

The staged hosts serve a certificate the image generates for names that resolve only on your machine, so the browser will warn. That warning is the honest signal that this is a local demo and not a deployment.

Install only what the service runs

A service that speaks to no broker leaves out Noelia.Messaging.MassTransit and never sees MassTransit. An architecture test pins the complete restored NuGet load of every package, including the zeroes, so growth is a reviewed decision rather than an invisible one. 

dotnet add package Noelia.Infrastructure
dotnet add package Noelia.Redis                    # or Noelia.InMemory
